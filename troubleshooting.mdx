Find the sentence you are looking at below. Each one is quoted as the product
says it, followed by what caused it and what changes the answer.

## A run refused because a window is full

The warning is titled with the window that refused — **5-hour limit reached** —
and reads *"You are going faster than your plan allows. Resets 12:19 PM UTC · in
4h 5m"*. If the window filled while the agent was already working, the run stops
where it is and the assistant's last message is the reason:

> You have used your 5-hour limit. It frees up at 12:19 UTC on 2 Sep 2026.

Nothing is lost. The messages, the tool calls and the files the agent wrote on
the machine all stay; send the message again after the reset and it picks up
from a machine that still has its work on it. Retrying sooner earns the same
refusal, and a new chat, a new machine or a second agent changes nothing,
because the windows belong to the account.

[When a limit is reached](/account/limits) has what lifts a window and what does
not.

## A machine that will not start

Two refusals are answers rather than faults, and neither is fixed by pressing
**Start** again.

**The plan already runs as many machines as it allows.** In the app:

> Your plan runs one machine at a time, and that one is taken. Delete a machine,
> or move up a plan.

Stopping a machine does not help and the product deliberately never suggests it:
the plan counts the machines an account *has*, and a stopped one still holds its
disk. This also happens on a machine that already exists — a plan can shrink
after the fact, and the machines that outlive a downgrade are still listed and
still one press from running. Which ones keep their slot is decided by most
recently used. Nothing is deleted.

**The machine's files are gone from the computer that held them.** In the app:

> The files this machine kept are not on the runner any more. Nothing was put in
> their place — an empty computer under the same name would look like a machine
> that had forgotten everything — so starting over here means creating a new
> machine.

There is no button that fixes this and no amount of retrying brings the disk
back. Create a new machine, give it the same agent, and start again.

Anything else is a fault on our side, worth [sending in](/support) with the
machine's name and the chat URL.

<Note>
Starting a machine by hand is rarely necessary. Sending a message in a chat on a
stopped machine starts it.
</Note>

## A tool that will not run until it is connected

A server on the **Tools** screen has a **Connect** button until you have signed
in to it. Until you do, the agent cannot use it, and opening its list of tools
may show only the generic *"The server encountered a problem and could not
process your request"* — not a helpful sentence, but the one you will see.
Press **Connect** and sign in.

Two other failures come from Splox rather than the service:

- *"The requested resource could not be found"* — the agent is reaching for a
  server you deleted, or one that is not on your account. Connect it again, or
  ask the agent to stop using it.
- *"… unknown system MCP service"* — the agent named a built-in service that
  does not exist. [The tools overview](/tools/overview) lists the ones that do.

If the server was connected and stopped working, your sign-in to it expired or
was revoked; the failure says so — *"OAuth re-authentication required: refresh
token expired or revoked"* — and reconnecting on the **Tools** screen is the
fix. See [connecting a server](/tools/connections).

## A push the agent's repository refuses

Your agent meets these when it publishes, and you meet them only if you clone
your agent's repository and push to it yourself. The repository holds a main line,
its published versions and drafts, and a push to anything else is refused before
it uploads, with the reason in git's output:

```text
 ! [remote rejected] HEAD -> scratch (a harness has main, versions and drafts, and refs/heads/scratch is none of them)
```

The other refusals of the same kind, as git prints them:

| What you pushed | What comes back |
| --- | --- |
| a deletion | `a harness ref is never deleted` |
| a version number | `a version is made by publishing, not by pushing refs/versions/7: commit your files and push main` |
| somebody else's draft | `that draft belongs to somebody else; yours is refs/drafts/<your-id>` |
| main together with another branch | `push main on its own: publishing it goes through refs/drafts/<your-id>` |
| main, from behind | `fetch first: main is 9e5d095 and this push is based on 4e91ca3` |

A push to main is a publish, and the publish is checked. Every problem is
reported together rather than one per try, starting with
*"refusing to publish: 1 problem(s) in the draft"* and then one line per
problem. The usual ones:

- **A file that does not belong.** The repository holds programs, tool files,
  eval cases and their graders, the dependency files and its own `.md`
  documentation at the root — and nothing else. A stray `notes/todo.txt` is
  refused.
- **No program at all.** An agent needs at least one program, the one that says
  which agent answers a chat.
- **Tools that would not load**, **two tools under one name**, or **an eval case
  naming a grader that does not exist** — a check that cannot fail would read as
  a pass, so it is refused instead.

Your work is not lost when a publish is refused: the draft keeps what you
pushed. Fix the files and push main again. [Publishing a
version](/inside/versions) covers the whole loop.

## A program that stopped when the machine did

A long-running program — a Telegram loop, a watcher, a nightly job — keeps
running after the turn that started it, through the next chat and into tomorrow.
It stops when the machine stops, and only then. Nothing ends it on a schedule
and no conversation ending takes it down.

So there are exactly two ways it dies: somebody pressed **Stop**, or the plan
behind the account stopped keeping machines running. On the free plan a machine
stops itself after 30 minutes with nobody talking to it, which is the usual
cause. From Pro up, machines are not stopped for being idle.

Ask the agent: *"Is the Telegram bot still running? Show me the last lines of
its log, and start it again if it stopped."* It checks on its own machine and
restarts the program the way it was started.

The lasting fix is in the program, not in the platform: ask the agent to write
it so that starting it twice is harmless and starting it after a stop picks up
where it left off, keeping its state in a file it reads on start. Then "has it
stopped?" stops being a question anybody has to answer.
[Programs](/reference/programs) shows the shape.

## An agent that cannot find a file it wrote

Four causes, in the order they actually happen.

**A tilde.** The agent's file tools do not expand `~`, so `~/notes` is not
found where `/home/daytona/notes` is. Name full paths when you name a file to
the agent; its home is `/home/daytona`.

**A sub-agent wrote it somewhere else.** A sub-agent given its own workspace
works in its own copy of the project, at `/home/daytona/workspace-<name>`, not
in the main `/home/daytona/workspace`. The files are there the moment the
sub-agent finishes; ask the agent to merge that workspace into the main one.
[Sub-agents](/reference/subagents) explains why the split exists.

**It wrote outside the home directory.** Everything outside `/home/daytona` is
read-only, so folders like `/work`, `/data` and `/app` are not there and never
were. Everything the agent creates belongs under `/home/daytona`.

**It ran on a different computer.** Work the agent did on your own computer, or
on a server it reached over SSH, is on that computer, not on the machine. So is
work done on a different machine: a chat stays on the machine it was started on,
and switching machines switches disks. [Machine](/concepts/machine) has the
rules for what is kept.

## A chat that says it is running when nothing is

First reload the page. The app reconnects to a run that is still going, and for
a run that finished while you were not looking, it shows what happened and
settles. A spinner that survives a reload with nothing new arriving usually
means the turn is over, however it ended.

If the run **is** genuinely working, a turn that spends minutes inside one tool
call looks identical to a stuck one from the outside; open the turn and read the
last tool call before you stop it.

To stop it, use the **Stop generating** button in the composer. Note that the
send button beside it is labeled *Send message (cancels current response)* and
does something different — it is easy to press the wrong one. A stopped turn
keeps the tool call it was in the middle of and gets no answer and no footer.

<Warning>
A turn that only produced failing tool calls has been seen showing as running
for several minutes after it had already ended. If a reload does not clear the
spinner and nothing new appears, nothing is running.
</Warning>
