Your agent has a computer, and a computer that runs code somebody else wrote is
a thing worth being precise about. This page says where that computer is, what
it can read, what holds the keys to the services you connect, and what leaves
it.

Every claim here is checked against the running system. Where something is not
checkable from outside, it is left out rather than reassured about.

## The machine is a sandbox of its own

A machine is one isolated computer of its own, with its own filesystem, its own
processes and its own network. It is not shared with another account and not
shared with another machine of yours: two machines are two computers with two
disks, and a second agent of yours runs on a machine of its own.

The card in the app reads **2 vCPU · 4 GB RAM** and a 30 GB disk. Inside it, the
agent's home is `/home/daytona`, and everything outside the home directory is
read-only: the agent cannot create files or folders there.

Everything the agent creates lives under the home directory, which is also
everything that survives a stop. See [Machine](/concepts/machine).

## What the agent can read

Anything on its own disk, and specifically:

| | |
| --- | --- |
| its own files | the agent's own code, prompts and tools, in the `harness` folder of its home |
| the tool packages and skills | what the platform gives every agent to work with |
| your secrets | the values you put on **Connections → Secrets**, handed to the machine so your programs can use them |
| the machine's own credential | what the machine uses to act for you on the platform (below) |

Secrets are the one kind of credential that is deliberately handed to the
agent: you add them so that a program or a tool of yours can use them, and the
agent can print any of them. They belong to whoever started the run, not to
the agent's owner, so a run somebody else started never shows your keys. Names
beginning with `SPLOX_` are refused when you save them (*"keys starting with
SPLOX\_ are reserved"*), so nothing you set can stand in for the platform's own
credentials. The agent can see which secret names it was given.

## The credential inside the machine is not your API key

Each machine carries a credential of its own, made for that machine and tied to
you as its owner. It does not expire, because a machine outlives every
conversation on it.

What it can do is narrow. It **cannot** reach your account: not your machines
list, not billing, not API keys, not connections. What it can do is what a run
needs — call the model, read the run's own history, save the agent's files, and
start runs and sub-agents as you and read what they produce. Each of those also
checks that the run or agent involved is the one the credential was made for.

So a leaked machine credential is a serious thing — it can start work as you —
but it is not an account API key, and it cannot create one. [API
keys](/account/api-keys) are separate, are created by you, and can be revoked.

## Where credentials for connected servers live

They stay on the platform. A connected server's credential is stored encrypted
(AES-256-GCM) and is never shown back — not in the app, not to the agent. The app
only tells you whether a server is connected and when its sign-in expires. When
the agent calls a tool on that server, the platform adds the credential to the
request on the way out. It is never written
into the sandbox and the agent cannot read it.

This is the opposite of environment secrets, which exist precisely to be read by
your own code. The rule of thumb:

| | Where it lives | Can the agent read it? |
| --- | --- | --- |
| A connected server's sign-in or key | platform, encrypted | no |
| A model provider key you added | platform, encrypted | no |
| A secret on **Connections → Secrets** | handed to the machine | yes |
| The machine's own credential | made per machine, on the machine | yes |

[Connections](/tools/connections) covers adding and revoking; a revoked
connection is a server whose next call has nothing to authenticate with.

## Who else can get into the machine

You can, two ways, both from the chat inspector and both time-bounded:

- **SSH.** You are given a one-time SSH command, and the access it grants lasts
  60 minutes. **Revoke access** ends it immediately.
- **An editor in the browser.** A signed link, good for an hour.

Both open the machine the conversation has already been working in, not a
fresh one. Nothing creates a computer for a chat that never needed one.

## What leaves the machine

Outbound network is open — the agent browses, installs packages, calls APIs. Two
things are worth knowing about it:

- Traffic the platform routes for the machine is tied to that machine, and
  sending mail directly is blocked (ports 25, 465, 587 and 2525). Nothing a
  browsing agent does needs SMTP, and an IP range that sends mail gets reported
  faster than anything else.
- The agent has [an email address and an SMS number](/tools/communication) of its
  own. Mail it sends goes out through the platform, under that address.

Separately from the machine, the text of a turn goes to a model provider —
whichever the run uses. On a model Splox provides that is Splox's
own account with that provider; on [your own connection](/app/connections) it is
your account and your key. What is sent, and to whom, is set out in the
[privacy policy](https://splox.io/privacy); [Data and
privacy](/data-and-privacy) is the operational summary.

## What a shared chat exposes

**Share** on a chat makes a link with a long random code in it (256 bits), in the
form `https://splox.io/chat/<code>`.

Anyone holding that URL reads the conversation with no account and no sign-in.
That is the whole of the access control: there is no per-person grant, no expiry
and no list of who opened it. What they see is the transcript — every message,
every tool call, and therefore every file path, command output and value the
agent printed along the way.

<Warning>
Share a chat the way you would share a document with no password. A transcript
carries more than the answers: the contents of files the agent read, the output
of a connected server, an id or a token that appeared in a tool call. Read the
turns before you send the link.
</Warning>

**Make private** turns the link off, and it stops working at once: anyone opening
the old link finds nothing.

Sharing again makes a **new** link. An old link stays dead, so revoking is real
rather than cosmetic. Deleting the chat kills the link too.

## What deleting actually deletes

<Steps>
<Step title="Deleting a machine">
The computer is destroyed first and only then removed from your list, in that
order, so no disk is ever left behind with nothing naming it. The disk goes with
it — notes, checkouts, databases, a program you left running. The harness is
untouched: it is the code, it is in git, and other machines may be running it.
Your chats are kept, though a chat whose machine was deleted has nothing to run
on.
</Step>

<Step title="Deleting a harness">
The repository goes, and so does every machine running it — a machine whose
harness is gone can never run again. Chats are kept.
</Step>

<Step title="Deleting a chat">
The chat stops being listed and stops being readable — for you, and through its
share link for everyone. It is marked deleted rather than erased, so this is
removal from the product, not erasure from our records. Erasure is
account deletion.
</Step>

<Step title="Deleting the account">
**Settings → Privacy → Delete account**, confirmed by typing the phrase. Every
machine you own is destroyed first — including ones you had already deleted —
any Stripe subscription is canceled immediately and your Stripe customer record
is deleted, and then, in one step, everything else goes: your chats, messages,
tool calls, runs, machines, connected servers, skills, push-notification registrations, webhooks,
sign-ins, wallet balance, transactions, subscriptions and usage. It is not
reversible.

Two things survive by design: the consent log, kept with your name removed as
the record that consent was asked for, and your agents' git repositories
themselves — deleting your account data has never deleted git history.
</Step>
</Steps>
